# Module 5 Patterns for Highly Autonomous Agents

## Planning workflows

Welcome to this final module where you learn about design patterns that lets you build highly autonomous agents, where you don't need to hard code in advance the sequence of steps to take, but it can be more flexible and decide for itself what steps it wants to take to accomplish a task. We'll talk about the planning design pattern and then later in this module, how to build multi-agent systems. Let's dive in. Suppose you run a sunglasses retail store and have information on what sunglasses are in your inventory stored in a database. You might want a customer service agent to be able to answer questions like, do you have any round sunglasses in stock? They're under $100. This is a fairly complex query because you have to look through the product descriptions to see what sunglasses are round, then look at what is in stock, and then finally see what's under $100 in order to tell the customer, yes, we have classic sunglasses. How do you build an agent to answer a broad range of customer queries like this and many others? In order to do so, we're going to give LLM a set of tools to let it get item descriptions, such as look up if different glasses are round, check inventory, maybe process item returns, which is not needed for this query, but we need it for other queries, get item price, check past transactions, process item sale, and so on. In order to let an LLM figure out what's the right sequence of tools to use to respond to the customer request, you might then write a prompt like this. You have access to the following tools and give it a description of each of the, say, six tools or even more tools that the LLM has, and to then tell it to return a step-by-step plan to carry out the user's request. In this case, to answer this particular query, a reasonable plan that an LLM might output might be to first use get item descriptions to check the different descriptions to find the round sunglasses, and then use check inventory to see if they're in stock, and use get item price to see if the in-stock results are less than $100. After an LLM outputs this plan with three steps, what we can do is then take the step one text, that is this text written here in red, and pass that to an LLM, maybe with additional context about what are the tools with your user query, with additional background context, and pass an LLM to carry out step one. And in this case, hopefully the LLM will choose to call the get item descriptions to get the appropriate descriptions of items, and the output of that first step can let it select which are the round sunglasses, and that output of step one is then passed together with the step two instructions, that would be these instructions that I have here in blue, to an LLM to then execute the second step of the plan. Hopefully it will then take the two pairs of round sunglasses we found on the previous slide and check the inventory, and the output of that second step is then used to another LLM call, where you have the output of the second step as well as the instructions of what to do for step three. Pass the LLM to have it get the item price, and finally this output is fed back to the LLM one last time to generate the final answer for the user. In this slide, I've simplified a lot of details a little bit. The actual plan typically written by the LLM is more detailed than these simple one-line instructions, but the basic workflow is to have an LLM write out multiple steps of a plan, and then task it to execute each step of the plan in turn with some appropriate surrounding context about what is the task, what are the tools available, and so on. And the exciting thing about using an LLM to plan this way is that we did not have to decide in advance what is the sequence in which to call tools in order to answer a fairly complex customer request. If a customer were to make a different request, such as I would like to return the gold frame glasses that I had purchased but not the metal frame ones, then you can imagine an LLM similarly being able to come up with a different plan to figure out based on what they had purchased previously, which glasses they had bought based on get item descriptions, where the gold frame ones they want to return, and then maybe call process item return. So with an agent that can plan like this, it can carry out a much wider range of tasks that can require calling many different tools in many different orders. One more example of planning, let's take a look at an email assistant. If you want to be to tell your assistant, so please reply to that email invitation from Bob in New York, tell him to attend and archive his email. Then an email assistant may be given tools like this to search email, move an email, delete an email, and send an email. And you might write an assistant prompt saying you have access to the following tools, and again please return the step-by-step plan. In this case, maybe the LLM will say the steps for this are to use search email to find the email from Bob that mentioned dinner and New York, and then generate and send an email to confirm attendance, and then lastly move that email to the archive folder. Given this plan, which looks a reasonable one, you would then again task an LLM step-by-step to carry out this plan. So the text from the first step, shown here in red, will be fed to the LLM with additional background context, and hopefully it'll trigger search email. Then the output of that can be given to an LLM again with the step two instructions to send an appropriate response. And then finally, assuming the email was sent successfully, you can take that output and have the LLM execute the third step of moving the email from Bob into the archive folder. The planning design pattern is already used successfully in many highly agentic coding systems, where if you ask it to write a piece of software to build some fairly complex application, it might actually come up with a plan to build this component, build this component, to almost form a checklist, and then do those steps one at a time to build a decently complex piece of software. For many other applications, the use of planning is still maybe more experimental. It's not in very widespread use. And one of the challenges of planning is it makes the system sometimes a little bit hard to control, because you as a developer, you don't really know at runtime what plan it will come up with. And so I think outside highly agentic coding systems, where it actually works really well, adoption of planning is still growing in other sectors. But this is exciting technology, and I think it will keep getting better and we'll see it in more and more applications. The cool thing about building agents that can plan for themselves is you don't need to hard code in advance the exact sequence of steps an LLM may take to carry out a complex task. Now, I know that in this video, I've gone over the planning process at a fairly high level, with it all putting a list of steps and then tasking an LLM to carry out the steps of the plan one step at a time. But how does this actually work? In the next video, we'll take a deeper dive to look further into the guts of what these plans actually look like, and how the strings together to have an LLM plan and execute the plan for you. Let's take a look at that in the next video.

## Creating and executing LLM plans

In this video, we'll look in detail at how to prompt an LLM to generate a plan, and how to read, interpret, and execute that plan. Let's dive in. This is a plan that you saw in the previous video for the customer service agents, and I have presented this plan at a high level using simple text descriptions. Let's take a look at how you can get an LLM to write very clear plans that go a little bit beyond these simple high-level text descriptions. It turns out that many developers will ask an LLM to format the plan it once executed in JSON format, because this allows downstream code to parse what exactly are the steps of the plan in relatively clear and unambiguous ways, and all of the leading LLMs are pretty good at generating JSON outputs at this point. So the system prompt might say something like this. You have access to the following tools, and then create a step-by-step plan in JSON format, and you might describe the JSON format in enough detail with the goal of getting it to output a plan like that shown here on the right. So in this JSON output, it creates a list where the first list item has clear keys and values that say step one of the plan has the following description, and it should use the following tool with the following arguments parsed to that tool. Then after that, step two of the plan is to carry out this task, and then use this tool, and so on. So this JSON format, as opposed to writing the plan in English, allows downstream code to more clearly parse out exactly what are the steps of the plan so that it can be reliably executed one step at a time. Instead of JSON, I also see some developers use XML, where you can use XML delimiters. You use XML tags to clearly specify what are the steps of the plan and what step number it is. Some developers, I feel like fewer developers, will use markdown, which is just sometimes slightly more ambiguous in terms of how we parse it, and I think plain text is maybe the least reliable of these options. But I think either JSON, which I'm showing here, or XML would be good options for how to ask the LLM to format a plan unambiguously. So that's it. By opening plans in JSON, you can then parse it and have downstream workflows execute different steps of the plan more systematically. Now, in terms of getting LLMs to plan, it turns out there's one other really neat idea that lets an LLM output very complex plans and get them executed reliably, and that's to let them write code and to have code express the plan. Let's take a look at this in the next video.

## Planning with code execution

Planning with code execution is the idea that, instead of asking an LLM to output a plan in, say, JSON format to execute one step at a time, why not have the LLM just try to write code and that code can capture multiple steps of the plan, like call this function, then call this function, then call this function, and by executing code generated by the LLM, we can actually carry out fairly complex plans. Let's take a look at when you might want to use this technique. Let's say you want to build a system to answer questions about coffee machine sales based on a spreadsheet with data like this of previous sales. You might have an LLM with a set of tools like these to get column max, to look at a certain column and get the maximum value, so there's a whole answer, what's the most expensive coffee, or get column mean, filter rows, get column min, get column median, sum rows, and so on. So these are examples of a range of tools you might give an LLM to process this spreadsheet or these rows and columns of data in different ways. Now, if a user were to ask which month had the highest sales of hot chocolate, it turns out that you can answer this query using these tools, but it's pretty complicated. You'd have to use filter rows to extract transactions in January for hot chocolate, then do stats on that, and then repeat for February, figure out stats on that, then repeat for March, repeat for April, repeat for May, all the way through December, and then take the max, and so you can actually string it together with a pretty complicated process using these tools, but it's not such a great solution. But worse, whether someone to ask how many unique transactions were there last week, well, these tools are insufficient to get that answer, so you may end up creating a new tool, get unique entries, or you may run into another query, what were the amounts of last five transactions, then you have to create yet another tool to get the data to answer that query. And in practice, I've seen teams, when they run across more and more queries, end up creating more and more and more and more tools to try to give the other enough tools to cover all the range of things someone may ask about a dataset like this. So this approach is brittle, inefficient, and I've seen teams continuously dealing with edge cases and trying to create more tools, but it turns out there is a better way, which is if you were to prompt LLM to say, please write code to solve the user's query and return your answer as Python code, maybe delimited with these beginning and ending execute Python XML tags, then LLM can just write code to load the spreadsheet into a data processing library, here it's using the pandas library, and then here it actually is coming up with a plan. The plan is, after loading the CSV, first it has to ensure the date column is parsed a certain way, then sort by the date, select the last five transactions, show just the price column, and so on. But these are the steps one, two, three, and four, and five, say, of the plan. Because a programming language like Python, and in this example, also with the pandas data processing library imported, because this has many built-in functions, hundreds or even thousands of functions, and moreover, these are functions that the LLM has seen a lot of data on how to call when. By letting your LLM write code, it can choose from these hundreds or thousands of relevant functions that it's already seen a lot of data on when to use, so this lets it string together different choices of functions to call from this very large library in order to come up with a plan for answering a fairly complex query like this. Just one more example. If someone were to ask, how many unique transactions last week? Well, you can come up with a plan to read the CSV file, parse the date column, define the time window, filter rows, drop duplicate rows, and count. The details of this aren't important, but hopefully what you can see is, if you read the comments here, the LLM is roughly coming up with a four-step plan and is expressing each of the steps in code that you can then just execute, and this will get the user their answer. So for applications where the task can plausibly be done by writing code, letting an LLM express its plan in software code that you can just execute for the LLM can be a very powerful way to let it write rich plans. And of course, the caveat that I mentioned in the module on tool use to consider if you need to find a safe execution environment like a sandbox to run the code, that also applies. Although I know that even though it's probably not the best practice, I also know a lot of developers that don't use a sandbox. Lastly, it turns out that planning with code works well. From this diagram adapted from a research paper by Xinyao Wang and others, you can see that for many different models for the tasks that they examined, code as action in which the LLM is invited to write code and take actions through code, that is superior to having it write JSON and then translate JSON into action or text. And you also see a trend that writing code outperforms having the LLM write a plan in JSON, and writing a plan in JSON is also a bit better than writing a plan in just plain text. Now, of course, there are applications where you might want to give your custom tools to an LLM to use, and so writing code isn't for every single application. But when it does apply, it can be a very powerful way for an LLM to express a plan. So that wraps up the section on planning. Today, one of the most powerful uses of Agentic AI that plans is highly agentic software coders. It turns out that if you ask one of the highly agentic software coding assistance tools to write a complex piece of software for you, it may come up with a detailed plan to build this component of software first, then build a second component, build a third, maybe even plan to test out the components as going along. And then it forms a checklist that then goes through to execute one step at a time. And so it actually works really well for building increasingly complex pieces of software. For other applications, I think the use of planning is still growing and developing. One of the disadvantages of planning is that because the developer doesn't tell the system what exactly to do, it's a little bit harder to control it, and you don't really know in advance what will happen at runtime. But giving up some of this control, it does significantly increase the range of things that the model may decide to try out. So this important technology is kind of cutting edge, doesn't feel completely mature outside of maybe agentic coding where it works well, although I'm sure there's still a lot of room to grow. But hopefully you enjoy using it in some of your applications someday. That wraps up planning. We have not just one agent, but many of them working in collaboration to complete the task for you. Let's take a look at that in the next video.

## Multi-agentic workflows

We've talked a lot about how to build a single agent to complete tasks for you. In a multi-agent or multi-agentic workflow, we instead have a collection of multiple agents collaborate to do things for you. When some people hear for the first time about multi-agent systems, they wonder, why do I need multiple agents? It's just the same LLM that I'm prompting over and over, or just one computer. Why do I need multiple agents? I find that one useful analogy is, even though I may do things on a single computer, we do decompose work in a single computer into maybe multiple processes or multiple threads. And as a developer, thinking, even though it's one CPU on a computer, say, thinking about how to take work and decompose it into multiple processes and multi-computer programs to run, that makes it easier for me as a developer to write code. And in a similar way too, if you have a complex task to carry out, sometimes, instead of thinking about how to hire one person to do it for you, you might think about hiring a team of a few people to do different pieces of the task for you. And so in practice, I found that for many developers of agentic systems, having this mental framework of not asking, what's the one person I might hire to do something, but instead, would it make sense to hire people with three or four different roles to do this overall task for me, that helps give another way to take a complex thing and decompose it into sub-tasks and to build for those individual sub-tasks one at a time. Let's take a look at some examples of how this works. Take the task of creating marketing assets, say you want to market sunglasses. Can you come up with a marketing brochure for that? You might need a researcher on your team to look at trends on sunglasses and what competitors are offering. You might also have a graphic designer on your team to render charts or nice-looking graphics of your sunglasses. And then also a writer to take the research, take the graphic assets and put it all together into a nice-looking brochure. Or to write a research article, you might want a researcher to do online research, a statistician to calculate statistics, a lead writer, and then an editor to come up with a polished report. Or to prepare a legal case, real law firms will often have associates, paralegals, maybe an investigator. And we naturally, because of the way human teams do work, can think of different ways that complex tasks can be broken down into different individuals with different roles. So these are examples of when a complex task were already naturally decomposed into sub-tasks that different people with different skills can carry out. Take the example of creating marketing assets. Look into detail into what a researcher, graphic designer, and writer might do. A researcher might have the task of analyzing market trends and researching competitors. And when designing the research agents, one question to keep in mind is what are the tools that the researcher may need in order to come up with a research report on market trends and what competitors are doing. So one natural tool that an agentic researcher might need to use would be web search. Because as a human researcher, asked to do these tasks might need to search online in order to come up with their report. Or for a graphic designer agent, they might be tasked with creating visualizations and artwork. And so what are the tools that an agentic software graphic designer might need? Well, they may need image generation and manipulation APIs. Or maybe, similar to what you saw with the coffee machine example, maybe it needs code execution to generate charts. And lastly, the writer has transformed the research into report text and marketing copy. And in this case, they don't need any tools other than what an LLM can already do to generate text. In this and the next video, I'm going to use these purple boxes to denote an agent. And the way you build individual agents is by prompting an LLM to play the role of a researcher or a graphic designer or a writer, depending on which agent it is part of. So for example, for the research agents, you might prompt it to say, you are a research agent, expert at analyzing market trends and competitors, carry out online research to analyze market trends for the sunglasses product and give a summary as well of what competitors are doing. So that would allow you to build a researcher agent. And similarly, by prompting an LLM to act as a graphic designer with the appropriate tools and to act as a writer, that's how you can build a graphic designer as well as a writer agent. Having built these three agents, one way to have them work together to generate your final reports would be to use a simple linear audit workflow or a linear plan in this case. So if you want to create a summer marketing campaign for sunglasses, you might give that prompt to the research agents. The research agent then writes a report that says, here are the current sunglasses trends and competitive offerings. This research report can then be fed to the graphic designer that looks at the data the research has found and creates a few data visualizations and artwork options. All these assets can then be passed to the writer that then takes the research and the graphic output and writes the final marketing brochure. The advantage of building a multi-agent workflow in this case is when designing a researcher or graphic designer or writer, you can focus on one thing at a time. So I can spend some time building maybe the best graphic designer agents I can, while maybe my collaborators are building research agents and writer agents. And in the end, we string it all together to come up with this multi-agent system. And in some cases, I'm seeing developers start to reuse some agents as well. So having built a graphic designer for marketing brochures, maybe I'll think about if I can build a more general graphic designer that can help me write marketing brochures as well as social media posts, as well as help me illustrate online webpages. So by coming up with what are the agents you might hire to do a task, and this will sometimes correspond to who are the types of human employees you might hire to do a task. You can come up with a workflow like this with maybe even building agents that you could choose to reuse in other applications as well. Now, what you see here is a linear plan where one agent, the researcher does his work, then the graphic designer, and then the writer. With agents, you can also, as an alternative to a linear plan, you can also have agents interact with each other in more complex ways. Let me illustrate with an example of planning using multiple agents. So previously, you saw how we may give an LLM a set of tools that we can call to carry out different tasks. In what I want to show you, we will instead give an LLM the option to call on different agents to ask the different agents to help complete different tasks. So in detail, you might write a prompt like you're a marketing manager, have the following team of agents to work with, and then give a description of the agents. And this is very much similar to what we're doing with planning and using tools, except the tools, the green boxes, are replaced with agents, these purple boxes that the LLM can call on. You can also ask it to return a step-by-step plan to carry out the user's request. And in this case, the LLM may ask the researcher to research current sunglasses trends and then report back. Then it will ask the graphic designer to create the images and then report back, then ask the writer to create a report, and then maybe the LLM will choose to review or reflect on and improve the report one final time. In executing this plan, you would then take the step one text of the researcher, carry out research, then pass that to the graphic designer, pass it to the writer, and then maybe do one final reflection step, and then you'd be done. One interesting view of this workflow is as if you have these three agents up here, but this LLM on the left is actually like a fourth agent that's a marketing manager, that is a manager of a marketing team, that is setting direction and then delegating tasks to the researcher, the graphic designer, and the writer agents. So this becomes actually a collection of four agents for a marketing manager agent coordinating the work of the researcher, the graphic designer, and the writer. In this video, you saw two communication patterns. One was a linear one where your agents took actions one at a time until you got to the end. And the second had a marketing manager coordinating the activity of a few other agents. It turns out that one of the key design decisions you may end up having to make when building multi-agentic systems is what is the communication pattern between your different agents? This is an area of hard research and there are multiple patterns emerging, but in the next video, I want to show you what are some of the most common communication patterns for getting your agents to work with each other. ## Communication patterns for multi-agent systems

When you have a team of people working together, the patterns by which they communicate can be quite complex. And in fact, designing an organizational chart is actually pretty complex to try to figure out what's the best way for people to communicate, to collaborate. It turns out, designing communication patterns for multi-agent systems is also quite complex. But let me show you some of the most common design patterns I see used by different teams today. In a marketing team with a linear plan, where first a researcher worked, then a graphic designer, then a writer, the communication pattern was linear. The researcher would communicate with the graphic designer, and in both the research and the graphic designer, maybe pass the outputs to the writer. And so there's a very linear communication pattern. This is one of the two most common communication plans that I see being used today. The second of the two most common communication plans would be similar to what you saw in this example, with planning using multiple agents, where there is a manager that communicates with a number of team members and coordinates their work. So in this example, the marketing manager decides to call on the researcher to do some work. Then if you think of the marketing manager as getting the report back, and then sending it to the graphic designer, getting a report back, and then sending it to the writer, this would be a hierarchical communication pattern. If you're actually implementing a hierarchical communication pattern, it'll probably be simpler to have the researcher pass the report back to the marketing manager, rather than the researcher pass the results directly to the graphic designer and to the writer. But so this type of hierarchy is also a pretty common way to plan the communication patterns, where you have one manager coordinating the work of a number of other agents. And just to share with you some more advanced and less frequently used, but nonetheless sometimes used in practice communication patterns, one would be a deeper hierarchy, where same as before, if you have a marketing manager send tasks to the researcher, graphic designer, writer, but maybe the researcher has themselves two other agents that they call on, such as a web researcher and a fact checker. Maybe the graphic designer just works by themselves, whereas the writer has an initial style writer and a citation checker. So this would be a hierarchical organization of agents, in which some agents might themselves call other sub-agents. And I also see this used in some applications, but this is much more complex than a one-level hierarchy, so used less often today. And then one final pattern that is quite challenging to execute, but I see a few experimental projects use it, is the all-to-all communication pattern. So in this pattern, anyone is allowed to talk to anyone else at any time. And the way you implement this is you prompt all four of your agents, in this case, to tell them that there are three other agents they could decide to call on. And whenever one of your agents decides to send a message to another agent, that message gets added to the receiver agent's contacts. And then a receiver agent can think for a while and decide when to get back to that first agent. And so if you can all collaborate in a crowd and talk to each other for a while until, say, each of them declares that it is done with this task, and then it starts talking. And maybe when everyone thinks it's done, or maybe when the writer concludes it's good enough, that's when you generate the final output. In practice, I find the results of all-to-all communication patterns a bit hard to predict. So some applications don't need high control. You can run it and see what you get. If the marketing brochure isn't good, maybe that's okay. You just run it again and see if you get a different result. But I think for applications where you're willing to tolerate a little bit of chaos and unpredictability, I do see some developers using this communication pattern. So that, I hope, conveys some of the richness of multi-agent systems. Today, there are quite a lot of software frameworks as well that support easily building multi-agent systems. And they also make implementing some of these communication patterns relatively easy. So maybe if you use your own multi-agent system, you'll find some of these frameworks hopeful for exploring these different communication patterns as well.
